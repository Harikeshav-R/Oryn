# Contribution and Synchronization Gateway — Detailed Specification Plan

## Context

Fully flesh out `docs/components/contribution-sync.md` as an implementation-ready technical specification, grounded in `PRODUCT.md` and `TECHNICAL.md`. Deliver detailed Markdown, machine-readable wire schemas, and reconciled adjacent ownership contracts; do not implement application software. The specification must let engineers implement approved contribution delivery, reviewed meeting handoffs, encrypted offline queues, truthful deletion races, authorized guidance caching, and revocation recovery without inventing protocol or policy. Identify the subsystem by filename: existing indexes number it differently from the user's phrase “fifth component”; do not renumber components.

The repository currently contains documentation, not application implementations or a runnable product test suite. The target brief has eleven top-level sections, confirmed by heading extraction. Preserve those section headings exactly, replace pending-design content, and mark it `Detailed technical specification — implementation pending`.

## Agreed decisions

These are execution requirements, not open options:

1. Personal-history-retention-off screen contributions are online-only. No durable sanitized payload exception bypasses the 30-second source lifetime or release fences.
2. Withdrawal immediately excludes unpublished accepted contributions from synthesis/publication and invalidates dependent unpublished proposals. Published derivatives use governed removal review; retention or holds do not permit continued synthesis from withdrawn records.
3. Employee review has no independent expiry. Exact reviewed content, purpose, audience, source eligibility, current authorization, and cancellation still gate transmission.
4. Private meeting-session identifiers remain local. No shared meeting-group identifier is introduced.
5. Run a dedicated signed, unprivileged Rust child, `oryn-sync-helper`, supervised by Desktop Shell. It never receives private evidence keys.
6. Use HTTPS request/response APIs and bounded long polling, not gRPC streaming.
7. A delivery receipt proves domain-owned durable acceptance, not publication, correctness, or recipient acceptance. Acceptance atomically commits payload, deduplication result, receipt, and outbox.
8. Default read-only offline guidance lease: 24 hours; policy may shorten it. No offline assist execution.
9. Store bounded accepted PNG attachments in PostgreSQL `bytea` columns within the domain acceptance transaction. No object-storage staging or presigned upload URLs on this path.
10. Transfer guidance manifest deltas plus complete immutable changed bundles. No binary patches.
11. Offline guidance promises a bounded, visibly reported working set, not all organizational playbooks. Prioritize active guide, recent use, then other authorized guidance.
12. Recover ambiguous delivery through status lookup first. Replay exact approved bytes under the same identity only while source and policy gates remain valid. After cancellation/deletion, send metadata-only reconciliation/withdrawal, never payload bytes.
13. Per-profile pending payload cap: 256 MiB and 1,024 submissions. Separate durable guidance cap: 256 MiB. Reserve admission space before committing an offline enqueue; never silently evict unsent approved content.
14. Add documentation-owned JSON Schemas and validate normative examples against them.
15. Keep a minimal replay ledger for the organization's lifetime: organization ID, submission ID/revision, content digest, terminal disposition. No narratives, images, private evidence IDs, or employee activity history. Erase it when the organization is permanently erased. Full receipts, attributable audits, and content follow separate retention schedules.

## Approach

### 1. Establish canonical contract vocabulary and machine-readable wire definitions

Create `docs/architecture/contracts/contribution-sync-v1.schema.json` and `docs/architecture/contracts/guidance-sync-v1.schema.json`. Discovery found no equivalent complete wire schemas: existing documents provide names, field lists, and examples only. These are normative contract documents, not product implementation.

Use JSON Schema Draft 2020-12 with `$id` values `urn:oryn:schemas:contribution-sync:v1` and `urn:oryn:schemas:guidance-sync:v1`. Put reusable definitions in `$defs`; top-level `oneOf` selects the publicly documented network objects by their exact `schema_id`. IPC payload definitions may live in `$defs` without becoming network-admissible root variants. Cross-schema references use those URNs and resolve through a local registry, never network retrieval. Close fixed objects with `additionalProperties: false`; only the explicitly bounded business-context map permits dynamic keys. Use structural validation plus the separately enumerated semantic checks below; do not claim JSON Schema verifies cryptography, DAGs, cross-field equality, aggregate bytes, u64 range, or authorization.

Shared primitives:

- `Identifier`: 1–128 ASCII characters, pattern `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. Existing actor/device/profile/team/application identifiers may remain opaque identifiers.
- `OrganizationId`: canonical lowercase UUID string. `ContributionId` and new request/attempt/receipt IDs: lowercase UUIDv4. Existing bundle IDs: canonical lowercase UUID, without requiring version 4. Do not convert unrelated application IDs or existing execution identities to UUIDs.
- `U64`: decimal string, pattern `^(0|[1-9][0-9]{0,19})$`, semantic maximum `18446744073709551615`; compare numerically, not lexicographically.
- `Sha256`: exactly 64 lowercase hexadecimal characters. This applies to content, artifact, manifest, and reviewed-content digest fields.
- Preserve `playbook_version` and `fix_playbook_version` as `sha256-` plus 64 lowercase hexadecimal characters, matching existing execution-context examples. Preserve unrelated action/assist-plan digest formats such as `sha256_...`; do not conduct a repo-wide digest-format migration.
- `Utc`: RFC 3339 UTC with `Z`; schema `format: date-time` plus semantic UTC check. `Signature`: unpadded base64url encoding of exactly 64 raw Ed25519 bytes; public keys encode 32 raw bytes. Decode and enforce lengths; placeholder signature prose is not a valid fixture.
- Human-readable narrative fields: plain text, no rendered HTML, maximum 4,096 Unicode code points unless a smaller bound appears below. Identifier arrays: unique, maximum 128 unless specified. No unrestricted JSON blobs, arbitrary paths, URLs, script expressions, DOM selectors, or private evidence IDs.

### 2. Specify approved custody, helper isolation, and the release/deletion linearization point

Expand the target's ownership, contracts, trust, architecture, and lifecycle sections. Reuse the inherited socketpair/anonymous-pipe pattern and code-signature verification established in `desktop-shell.md` and ADR-0001; do not add a localhost server, named sync pipe, browser endpoint, privileged daemon, or independent system service.

Topology:

- Shell supervises `oryn-sync-helper` and creates two private inherited channels, protocol `shell-sync.v1`, major 1/minor 0: control/status and approved-bundle data relay.
- Shell also creates a separate direct privacy↔sync link, protocol `privacy-sync.v1`, major 1/minor 0, with independent control and payload channels. This does not repurpose or renumber the existing four shell↔privacy channels or Contract 25.
- Committed guidance travels sync→shell→HUD over existing Contract 20 bulk-data rails. Shell relays opaque bounded chunks; it is not cache, signature, or authorization authority. HUD revalidates the committed generation and signatures.
- `SessionBroker` alone keeps refresh credentials. Sync receives short-lived access tokens, audience-bound to the control plane and restricted to sync enrollment/read/write, guidance read, and own contribution withdrawal. It never receives provider secrets, refresh tokens, privacy catalog credentials, raw capture paths, or private dependency IDs. Public device review keys, not private signing keys, may cross into sync.

Use four-byte big-endian length-prefixed UTF-8 JSON. Envelope fields: `protocol`, `major`, `minor`, `type`, `request_id` (UUIDv4 or null for events), `session_epoch` (UUID), `sequence` (U64), `payload`. Reject duplicate JSON keys, unknown fields, invalid UTF-8, excessive nesting, mismatched epochs, and malformed lengths. All endpoints negotiate exact major 1/minor 0 mandatory capabilities; incompatibility disables sync with `SYNC_PROTOCOL_UNSUPPORTED`, not capture. Control frames ≤256 KiB, 64 queued messages / 1 MiB, eight slots reserved for cancellation/restrictions. Data frames ≤1 MiB, 16 queued messages / 8 MiB; binary bytes use base64url chunks with at most 256 KiB decoded bytes per chunk. Enforce total decoded lengths against declared manifests before allocating. Backpressure bulk data; never drop privacy/revocation control messages to admit payload chunks. Heartbeats every 100 ms; 500 ms silence or EOF stops new dispatch, aborts active transmissions best-effort, and preserves uncertainty. Sync failure must not pause healthy capture; valid read-only cached guidance may remain available until lease expiry.

Document exact logical commands and their request/result fields in the contribution schema `$defs`:

- `ReserveQueueSlot {contribution_id, revision, content_digest, byte_length, custody_mode: durable|volatile, source_not_after: Utc|null}` → `{reservation_id, custody_mode, not_after}` or `SYNC_QUEUE_FULL`. Privacy selects mode; retention-off screen mode must be volatile. Reserve at most 30 seconds, clamped to source eligibility. Charge receiving slots to quotas. No slot means approval is not reported as safely queued.
- `EnqueueReviewedContribution {reservation_id, custody_mode, envelope, transfer_id, total_bytes}` plus bounded `PayloadChunk {transfer_id, index, decoded_length, bytes_base64url}` and `CommitEnqueue {transfer_id}` → `{queue_entry_id, contribution_id, revision, content_digest, custody_mode, acknowledged_at}`. Durable mode acknowledges only after durable commit. Volatile mode acknowledges locked-memory custody only and permits no capsule/database/blob payload writes. Exact duplicate identity/digest/mode returns the original acknowledgment; conflicting digest or mode is `SYNC_DIGEST_CONFLICT`.
- `BeginRelease {contribution_id, revision, content_digest, attempt_id, control_epoch, control_sequence}` → `SignedReleasePermitV1` or cancellation/stale-policy rejection. Privacy helper transactionally checks the exact active fence, dependency existence/revisions, source deadline, current sharing consent/policy, artifact scope, and current session, then marks the projection `dispatching`. That transaction is the dispatch linearization point, before initiating the HTTP body.
- `CancelRelease {contribution_id, revision, reason, deletion_generation}` is authoritative privacy control. Reasons are `source_deleted|source_expired|source_changed|sharing_revoked|employee_withdrawal|policy_restricted|session_ended|helper_lost`. Persist the reason. Before `BeginRelease` commits, cancellation guarantees zero contribution-body bytes. After it commits, abort best-effort and mark `delivery_unknown` unless a definite non-send or definitive receipt is established. A source expiry is not automatically a withdrawal of already accepted knowledge. Session/helper interruptions are transport failures, not employee withdrawal.
- `RecordDelivery {contribution_id, revision, attempt_id, receipt_or_signed_status}` → privacy acknowledgment after signature/identity/digest verification. Sync retains the complete local approved payload until durable server acceptance and this local acknowledgment; if source cancellation already happened, only metadata remains and reconciliation cannot require it.
- `GetReleaseState {contribution_id, revision}` supports crash recovery without reading private sources in sync. Privacy returns active/cancelled/released, current digest, projection, and an eligibility deadline; never private dependency identifiers.
- `GetReviewPublicKeys {key_ids: Identifier[1..128]}` → `{keys:[{key_id,public_key}]}` over the verified private privacy↔sync link supplies public keys needed for offline queue signature checks. It does not enroll or authorize those keys centrally. Before dispatch, sync also matches the key against current signed bootstrap registry state; server independently verifies the authoritative enrollment. Never accept a public key embedded in an untrusted network contribution as its own trust proof.

`SignedReleasePermitV1`, schema ID `sync.release-permit.v1`, uses the current registered device key. Payload: Identity, contribution ID/revision/digest, review receipt ID, attempt ID, control epoch/sequence, current sharing policy/access revisions, `artifact_policy_revision: Identifier|null` for the current artifact policy, `issued_at`, `not_after`. Maximum 30 seconds, clamped to finite source expiry, access-token expiry, and control-snapshot deadline. One permit authorizes one attempt; retry requires a fresh permit/attempt with the same contribution idempotency identity. Validate current authorization and expiry again at the final locked acceptance decision, not just HTTP header admission.

Custody crash protocol:

1. Privacy helper owns review and establishes the active source fence before offering bytes. Durable custody commits the reviewed envelope/fence to encrypted storage; volatile custody keeps envelope/source fence only in locked memory and may persist content-free attempt identity after dispatch. Neither shell nor sync manufactures review events or signatures.
2. With retention enabled, privacy persists a bounded sanitized dispatch capsule in its control store until durable enqueue acknowledgment, then removes that transport capsule. The capsule is reviewed data, not another raw capture archive; cap it to one 5 MiB submission and retain private dependency IDs only on the privacy side.
3. Sync atomically commits its encrypted payload and queue row, then acknowledges. Re-offering after an acknowledgment loss deduplicates by ID/revision/digest. On startup, validate every queued row against privacy fences before release.
4. Reservation/transfer expiry discards incomplete chunks and releases capacity. A source cancellation during transfer cancels the fence and destroys partial reviewed copies. A new review revision cannot reuse a permit for an older digest.
5. Retention-off screen contributions bypass durable capsules and offline queue payload storage. Hold approved bytes only in locked volatile buffers within the original 30-second source deadline. One immediate source-valid dispatch may proceed; expiry aborts it and destroys bytes. Persist only content-free uncertainty/status identifiers if needed for reconciliation, never sanitized narrative/image buffers. Meeting handoffs retain their separately governed meeting-source behavior; screen-retention-off does not disable independently authorized meeting storage.

Reconcile `local-privacy-storage.md`'s `release_fences` table and deletion-race prose: retain private-only dependency IDs; add `withdrawal_requested` to delivery projections plus nullable `active_attempt_id`, `dispatch_started_at_utc`, `eligibility_not_after`, and `cancellation_reason` using the enum above. Fence states remain `active|cancelled|released`; `released` means confirmed domain acceptance, not permission issuance. Source edits/expiry/deletion cancel unreleased fences. A valid server acceptance before natural source expiry remains delivered even when acknowledgment arrives afterward; explicit deletion or an invalidated source during dispatch still requests withdrawal. Ordinary expiry of sources for an already delivered contribution never automatically retracts organizational knowledge.

PostgreSQL acceptance algorithm:

1. Authenticate and verify current membership, sharing scope, signed review, registered key, permit, artifact policy, typed content, bounded bytes, and artifact digests. Never log rejected payload contents.
2. Begin READ COMMITTED. Acquire organization/access, member/device/key, then applicable artifact-policy guard rows in deterministic key order using `SELECT ... FOR SHARE`; reread current authorization, member/device/key status, policy/artifact permissions, revisions, and deadlines after waits. Restriction writers take `FOR UPDATE` on the same rows before mutation. Hold those guards through commit; then create/lock the submission identity row using `FOR UPDATE`. No network upload occurs while these locks are held.
3. If identity is tombstoned/withdrawn, reject admission; late bytes cannot restore eligibility. If already accepted with same identity/digest, return the stored response without re-enqueuing discovery. A conflicting digest is terminal.

They bind every completion to that generation; withdrawn/stale generations cannot commit draft results. Duplicate messages cannot duplicate candidates/handoffs. Graph recipient acceptance also locks and revalidates the submission identity before creating an accepted obligation. Delivery does not wait for interpretation or recipient acceptance.
