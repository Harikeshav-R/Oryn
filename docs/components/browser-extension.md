# Browser Extension and Local Browser Bridge Component Brief

Status: Baseline brief — detailed design pending

## Purpose and ownership

**Source references:** [TECHNICAL.md §4.3](../../TECHNICAL.md) | [PRODUCT.md §§3.3, 3.6, 8, 12, 25; ORY-005, ORY-019, ORY-028](../../PRODUCT.md)

### Core Responsibility
The Browser Extension and Local Browser Bridge capture high-fidelity, permissioned browser context for supported Chrome and Edge business applications, enable non-intrusive contextual guidance overlays, and facilitate approved browser actions where authorized.

### Owns
- Browser-side DOM observation, tab lifecycle tracking, and page context extraction for permitted web applications.
- Local communication bridge connecting the browser extension to the desktop companion services via native messaging or secure local IPC.
- Highlighting element targets and rendering step guidance within approved browser web pages.

### Consumes
- Domain allowlists and exclusion policies from [local-privacy-storage](local-privacy-storage.md).
- Authenticated local desktop companion session tokens from [desktop-shell](desktop-shell.md).
- Published guidance step definitions and element selector rules from [local-context-hud](local-context-hud.md).
- Authorized browser action requests originating from [agent-runtime](agent-runtime.md) or local executor.

### Produces
- Structured DOM observation events, form field interactions, and navigation markers.
- Contextual element anchors and bounding box coordinates for guidance rendering.
- Execution results of authorized browser assistance actions.

### Does Not Own
- Central organizational knowledge sharing or direct cloud egress (owned by [contribution-sync](contribution-sync.md)).
- Independent autonomous job scheduling or unconstrained browser navigation (owned by [job-orchestration](job-orchestration.md)).
- Granting permissions to act beyond a declared job scope (owned by [identity-policy](identity-policy.md)).

### Boundary Requirement
Browser observations must be correlated or deduplicated with OS-level observations when describing the same user action. The extension must enforce the exact same privacy exclusions and data minimization rules as native OS observers before transmitting observations to the local companion.

## Product requirements

### Key Product Requirements ([PRODUCT.md §§3.3, 3.6, 8, 12, 25; ORY-005, ORY-019, ORY-028](../../PRODUCT.md))
- **Domain-Level Exclusions:** The extension must immediately disable observation when navigating to personal email, banking, health, or private browsing tabs (ORY-005).
- **Accurate Step Guidance:** When presenting guided assistance in a web application, the extension must point directly to the correct business input element and refrain from advancing if an action fails (ORY-019).
- **Scope Restriction:** Browser automation actions must be restricted strictly to declared domains and target records; cross-domain navigation during execution is blocked (ORY-028).

## Upstream and downstream contracts

**Catalog reference:** [Cross-Component Contracts Catalog](../architecture/contracts/README.md)

### Cross-Component Contracts
- **Contract Reference #1 in [Contracts Catalog](../architecture/contracts/README.md):** Emits raw candidate browser observations to [local-privacy-storage](local-privacy-storage.md).
- **Local Bridge Protocol:** Exchanges authenticated messages with [desktop-shell](desktop-shell.md) and [local-context-hud](local-context-hud.md) over native messaging or local loopback.
- **Guidance Target Contract:** Receives element selector criteria from [local-context-hud](local-context-hud.md) and returns resolved element presence and viewport coordinates.

## Trust and deployment boundaries

### Process and Security Boundaries
- **Deployment Location:** Executes inside Google Chrome and Microsoft Edge browser sandboxes as a Manifest V3 extension, paired with a local native messaging host.
- **Data Access:** Restricted to approved web origin domains declared by enterprise policy. Inactive on private browsing tabs and non-approved domains.
- **Local Bridge Authentication:** Local bridge communication is authenticated with ephemeral session tokens generated by the desktop companion to prevent unauthorized local processes from interacting with the extension.
- **Cloud Egress:** The extension has zero external network permissions; all data flows exclusively through the local native messaging bridge to the local companion.

## Internal architecture

### Logical Submodules
- **Content Script Observer:** Monitors DOM mutations, input events, and form changes on allowlisted web pages.
- **Exclusion and Masking Filter:** Masks sensitive input fields (password, credit card, SSN) directly inside the content script before serialization.
- **Guidance Overlay Injector:** Renders visual highlights and tooltips anchored to target DOM elements.
- **Native Messaging Bridge Client:** Handles serialization and bidirectional communication with the local companion host.

## State and lifecycle

### State and Persistence
- **Persisted State:** Minimal local extension storage for cached domain allowlists and local bridge pairing tokens.
- **Lifecycle Transitions:** `Unpaired → Paired → Inactive (Non-approved Domain) ↔ Observing (Approved Domain) ↔ Executing Authorized Action`.
- **Page Navigation:** State reinitializes cleanly on page reload or cross-origin navigation, re-evaluating domain eligibility immediately.

## Error and edge-case behavior

### Failure Handling
- **Bridge Disconnection:** If the native messaging bridge to the desktop shell drops, the extension enters a dormant state and disables in-page guidance.
- **DOM Drift / Missing Elements:** If a guidance selector fails to resolve, the extension reports an element-not-found error to the HUD rather than anchoring to a wrong element.
- **Content Script Injection Failure:** Detected by the background worker and reported as a degraded observation state.

## Observability and audit

### Telemetry and Diagnostics
- Diagnostic logs record bridge connection status, DOM query performance, and selector match rates.
- Diagnostic logs never contain customer form input values or private web page URLs.

## Security and threat model

### Security and Safety Considerations
- **DOM Injection Attacks:** Malicious web pages must not be able to execute arbitrary scripts in the extension context or send unauthorized commands across the native bridge.
- **Cross-Tab Leakage:** Content scripts in different tabs remain completely isolated; observations from one tab cannot be injected into another.
- **Sensitive Field Shielding:** Input fields marked as type=password or matching sensitive patterns are masked prior to transmission across the bridge.

## Test strategy

### Acceptance and Verification Scenarios
- **Acceptance Criteria References:** [PRODUCT.md §31.1: ORY-005; §31.2: ORY-019; §31.3: ORY-028](../../PRODUCT.md).
- **Concrete Verification Scenario:**
  - *Input/Condition:* User opens an enterprise invoice approval portal in Chrome; the extension detects an approved domain; user fills an invoice number and attempts to navigate to an unauthorized domain.
  - *Expected Observable Result:* DOM input events for the invoice form are captured and routed across the local bridge; when navigation to the unauthorized domain occurs, observation immediately ceases and no data from the unauthorized domain is emitted.

## Performance and operations

### Operational Characteristics ([TECHNICAL.md §12](../../TECHNICAL.md))
- Content script execution must not degrade page scroll rate or input responsiveness.
- DOM queries must utilize efficient mutation observer throttling to prevent CPU spikes on dynamic single-page applications.

## Architecture decisions and open questions

### Specific Preserved Implementation Questions
- What exact native messaging protocol or localhost transport minimizes latency between browser content scripts and the desktop companion?
- How should robust DOM selector generation balance CSS selectors, XPath, ARIA attributes, and structural heuristics?
- What permissions model should be requested in the browser extension manifest to satisfy enterprise security review?
- How should correlation between OS accessibility events and browser DOM events be achieved cleanly?

### Handoff Questions ([TECHNICAL.md §14.2](../../TECHNICAL.md))
1. *Owns exclusively:* In-browser DOM observation, web guidance overlay rendering, and browser native messaging bridge.
2. *Data ingress/egress:* Ingests DOM mutations and guidance commands; emits structured browser observation events to local privacy storage.
3. *Versions/identities:* Extension manifest version, browser build identity, tab ID, and target origin URL.
4. *Upstream failure:* If desktop companion is unavailable, extension becomes dormant and ceases all observation.
5. *Authority:* Desktop companion governs extension enablement; [identity-policy](identity-policy.md) governs action rights.
6. *Testing without private details:* Tested using synthetic web fixtures and automated browser testing suites (Playwright/Puppeteer).
7. *Audit and duplicate prevention:* Observations carry tab sequence IDs to detect duplicates and dropped events.
8. *Failure blast radius:* Extension crash or failure is contained to browser tabs; does not affect desktop shell or OS observer.
9. *v1.0 criteria:* Enables ORY-005, ORY-019, and ORY-028 verified via in-browser guidance and domain boundary tests.
