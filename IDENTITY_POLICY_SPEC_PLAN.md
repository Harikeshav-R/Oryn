## Approach

Execute the following behavior slices in order. Slices 1–7 define the target specification and new contract; slice 8 reconciles their consumers. Existing code does not implement this module. All Rust symbols below are proposed interfaces to document, not claims about existing source files.

### 1. Establish identity ownership, authentication, and session isolation

Commit to one Oryn-managed reference deployment. Identity is a Rust logical module inside the modular control plane, backed by PostgreSQL, with a pure typed evaluator. No customer policy language, custom-role editor, external policy service, or authoritative permission cache. Do not choose a frontend framework, model provider, orchestration engine, or general infrastructure topology through this specification.

Ownership:
- Auth0 handles login, SAML/OIDC federation, passwordless email, and MFA. Its claims prove authentication, not Oryn membership, roles, capture consent, publication rights, or execution authority.
- Control Plane owns HTTP/BFF handling, physical session persistence, request authentication, idempotency transport, and outbox delivery. Identity owns session admission/expiry policy, verified principal construction, memberships, authorization, and formal approval validity.
- Desktop `SessionBroker` owns native credentials. Privacy Helper owns local consent enforcement, review keys, evidence, and release fences. Sync only transports public enrollment data and authorized artifacts.
- Release Governance owns readiness evidence and released-version eligibility. Identity defines/checks authorization policy and approval records, not evaluation outcomes. Outcome Verification owns business truth. Infrastructure owns Vault, service credentials, and audit archive operation.

Authentication flow:
1. Use Auth0 Universal Login in the external system browser. Native application is a public client using Authorization Code + PKCE `S256`, state and OIDC nonce. No embedded login WebView or desktop client secret.
2. Native callback binds `127.0.0.1` before opening the browser; choose a random available port from the registered range 49152–49183, exact path `/callback`. Register the exact 32 callback URIs, not arbitrary redirect wildcards. If none binds, report login unavailable; do not use a public listener, custom scheme, or insecure fallback. The bounded port pool concretizes the existing random-loopback callback without depending on unverified arbitrary-port acceptance.
3. A server-created login transaction lasts five minutes, binds client kind, selected organization if known, state, nonce, and allowed callback. Validate issuer, RS256 allowlist, signature/JWKS key, audience/client, expiry, nonce, state, and transaction single use. Unknown key permits one bounded refresh from the configured Auth0 issuer; token-supplied `jku`/`x5u` never select a URL.
4. Auth0 passwordless email code supports initial setup and invitations. Use broker-hosted UI and configured production SMTP; Auth0's test mail provider is not a deployment prerequisite substitute. Once organization SSO is enforced, ordinary email login cannot satisfy that organization's session admission. Auth0 native callback confirmation stays enabled; no silent `prompt=none` workaround.
5. Use Oryn-owned opaque 256-bit random session/access/refresh secrets after login admission. Store SHA-256 token digests, never bearer values, in the control-plane session store. Initial Auth0 tokens are validated then discarded; do not create a second long-lived Auth0 refresh channel. Oryn refresh rotates credentials atomically and never extends the original absolute login deadline. Refresh replay revokes its session family and emits a security event.
6. Oryn child access tokens last at most five minutes, bind audience, session, organization, actor, device/profile when applicable, and an explicit scope subset. Sync retains its existing scope strings. Children never receive refresh secrets, another audience's token, or all user permissions. Every privileged request loads current Oryn authority; a valid bearer alone is insufficient.
7. Web uses a BFF and `Secure`, `HttpOnly`, `SameSite=Lax`, `__Host-` session cookies, same-origin checks, and CSRF tokens for mutations. Native bearers remain in Rust/OS credential storage, never React. Web login lasts at most 12 hours, with a server-enforced 30-minute human-inactivity lock. Desktop login lasts at most seven days. Refresh/background capture does not reset a human-activity clock. Organizations may shorten these bounds.
8. Tier 3 approvals, releases, permission expansion, privileged-role/SSO/recovery changes, legal-hold administration, and organization deactivation require independently verified MFA completed within five minutes. Use Auth0 WebAuthn MFA or TOTP, not email/SMS as the independent factor for email-code login. Auth0 post-login Actions emit exact signed namespaced claims `https://oryn.app/claims/connection_id` from `event.connection.id`, `https://oryn.app/claims/connection_strategy` from `event.connection.strategy`, and `https://oryn.app/claims/mfa_at` from the latest completed broker MFA event timestamp. A challenge Action precedes the claim-emitting Action. Missing/stale MFA evidence gives a step-up requirement; token refresh never resets its timestamp. Backend accepts only connections explicitly configured for the selected organization and binds step-up transactions to the existing Oryn session and same linked person. Enforcing SSO invalidates sessions authenticated through now-disallowed connections. Do not infer enterprise MFA from an arbitrary `amr`; broker MFA remains the default proof. Validate broker time claims against trusted server UTC with at most 30 seconds future skew, but never add grace after authority expiration.

Identity model:
- Global private login-subject mapping is keyed by exact `(issuer, subject)`. It maps to a private person identifier; email is mutable contact data, never identity authority.
- Each organization has its own `actor_id` membership, teams, grants, policy, and external-connection admission mapping. A person can have multiple memberships; role union never crosses organizations. Matching emails never auto-link accounts or grant membership.
- Existing users authenticate their currently linked subject to accept an invitation. Switching to a new SSO subject uses an explicit link transaction proving both identities; otherwise an Organization Admin issues a replacement invitation to the new subject and suspends the old membership after ownership transfer. Never merge by domain/email or silently copy grants.
- Invitation secrets are random 256-bit values stored as digests, one-use, seven-day expiry, with explicit intended organization, email, inviter, and proposed roles/scopes. Email possession verifies the invitation destination, not a preexisting account merge. Role assignment is a fresh authorized transaction at acceptance; revoked inviter authority or changed invitation invalidates acceptance.
- The authenticated creator may create an organization in `restricted` state and explicitly accept initial Organization Admin and Security Admin duties with recent MFA. Creating a workspace does not enable capture, inference, or writes. Activation requires configured security policy and at least one explicitly assigned Workflow Owner.
- Exactly one organization/employee profile is active per OS desktop user. Switching requires explicit sign-out of the prior organization, stopped capture/meeting, safe execution containment, cleared tokens/caches, locked prior private profile, and fresh browser pairing. Old profile data remains encrypted; new session cannot unlock it.
- Ordinary token expiry leaves local private history and privacy controls available per the desktop contract. Explicit sign-out locks history. Role/membership restriction stops affected organizational access/capture without granting an administrator private-history access or destroying private keys.

### 2. Define fixed roles, typed policy, and denial precedence

Use these role IDs, with the existing product display names: `employee`, `sme`, `agent_operator`, `workflow_owner`, `automation_builder`, `operations_manager`, `security_admin`, `organization_admin`, `read_only_stakeholder`.

The fixed public capability catalog is:
`playbook.read`, `workflow.review`, `rule.approve`, `agent.edit`, `job.run`, `action.approve`, `incident.review`, `repair.approve`, `release.approve`, `analytics.read`, `report.export`, `privacy_policy.manage`, `membership.manage`.

Add bounded internal operations `schedule.manage`, `audit.read`, `security_policy.manage`, `hold.manage`, and `identity.recover` where required by their explicit ownership. Transport scopes such as `sync:contribute` are necessary token restrictions, not independent role grants.

Document this role-maximum matrix; all organizational resources still require audience/team/workflow scope:
- Employee: `playbook.read`, own privacy/contribution controls, and explicitly released/authorized assist sessions. No production `job.run` from this role.
- SME: Employee plus `workflow.review`; explanations/proposals do not confer `rule.approve`.
- Agent Operator: Employee plus `job.run`, scoped `incident.review`, and `action.approve` only under a matching active approval delegation.
- Workflow Owner: Employee plus assigned `workflow.review`, `rule.approve`, `incident.review`, `repair.approve`, `release.approve`, and `schedule.manage`; action approval additionally requires explicit delegation. Job execution additionally requires the operator role.
- Automation Builder: Employee plus `workflow.review` and `agent.edit`; may propose tests/repairs/releases but cannot approve release through this role.
- Operations Manager: team-scoped `playbook.read`, `analytics.read`, and read-only assigned issue/incident status. Manager status is not action approval or raw-evidence access.
- Security Admin: `privacy_policy.manage`, `security_policy.manage`, `audit.read`, `hold.manage`, plus policy-side permission-expansion approval; no implicit business-rule/release-owner authority.
- Organization Admin: `membership.manage`, team/ownership administration, and identity configuration; no implicit action approval, business-rule approval, or private evidence rights.
- Read-Only Stakeholder: explicitly shared `playbook.read` and eligible report/status reads, no writes/execution/export by default.
- `report.export` requires an explicit capability grant from an authorized security policy, within an existing report-read scope. Its absence denies export even if the actor can see a dashboard. Granular grants may enable only capabilities within these role maxima, except this explicit export-policy grant.

Assignments carry organization, subject actor, role, scope, effective interval, grantor, reason, and revision. Scope is a closed typed selector containing nullable team/workflow/application IDs and an optional finite record-ID allowlist (at most 1,000). Null means no narrowing on that dimension, never an absent organization. Conditions within a grant intersect; matching grants union; any applicable explicit deny removes permission. No inherited access follows graph links or team handoffs.

A delegation is separate from role assignment: approver, allowed action types, team/workflow/application/record types, validity interval, optional per-item amount cap and currency, and optional distinct-initiator requirement. Amount is a nonnegative decimal integer minor-unit string within signed 64-bit range plus an explicit three-letter currency. Require known amount/currency when an amount policy applies; no floating point, FX conversion, guessed threshold, or split-action downgrade. Separate the power to establish a delegation from the power to exercise it: Security Admin plus applicable Workflow Owner may establish the first delegation within explicitly approved policy ceilings without already holding action-approval delegations themselves. Operators/owners cannot redelegate. Later expansion uses the same two authorized remits, never a delegated approver's inferred authority. The same person may satisfy both remits unless organization policy requires distinct humans.

A job initiator or assist employee may approve its own staged action only with a valid explicit delegation. A Tier 3 release always requires a Workflow Owner distinct from its proposer. Other administration uses one authorized administrator plus recent MFA by default; an organization may impose stronger separation. Evaluate the old policy when authorizing removal of an existing separation requirement, so editing policy cannot bypass that requirement.

Represent policy as immutable, schema-checked typed records, not strings or executable expressions. Define closed configuration for session bounds, allowed applications/actions/tiers, mandatory exclusions, capture/sharing/meeting restrictions, retention/artifact limits, delegation/separation rules, bulk allowlists, and inference route/purpose/budget policy. New organizations default to no capture consent, no application execution, no inference budget, and no bulk approval. Missing customer financial/action policy remains restricted. Mandatory product exclusions and Tier 4 prohibition are non-overridable code guards.

Document the proposed pure Rust interface:
```rust
fn evaluate_authorization(
    snapshot: &AuthorizationSnapshotV1,
    request: &AuthorizationRequestV1,
    now: UtcInstant,
) -> PolicyEvaluationV1;
```
`AuthorizationSnapshotV1` is built only from trusted current owner records; callers cannot supply roles, classify an action downward, or assert release/readiness. `PolicyEvaluationV1` is a private unsigned result `{verdict: Allow|Deny|RequireHumanApproval, reason_code, risk_tier: Option<RiskTier>, policy_revision, access_revision, required_approval: Option<ApprovalRequirementV1>, rule_checks, authority_checks}`; `ApprovalRequirementV1` contains exact action/proposal inputs and required remits, not signed bytes. The transactional service loads state, evaluates, persists/signs via Vault, and only then constructs public `AuthorizationDecisionV1`. `UtcInstant` is a validated UTC instant, not an unchecked string.

Evaluation order is fixed: authenticated workload/human and environment → active organization/membership/session/device → tenant/resource equality → mandatory prohibition → current allowed scope and role capability → explicit denies → trusted effective risk → released version/assist eligibility and current rule constraints → amount/delegation/separation constraints → required approval. Missing/indeterminate inputs deny. Only otherwise-permitted actions lacking a required approval return `RequireHumanApproval`; forbidden actions never open an approvable escape hatch. Tier 0 still requires read authority; Tier 4 always denies automated execution.

### 3. Specify exact authorization, approval, and dispatch contracts

Create `docs/architecture/contracts/identity-policy-v1.schema.json`, Draft 2020-12, `$id` `urn:oryn:schemas:identity-policy:v1`. No equivalent identity/action/capture/retention wire schema exists in the inspected contracts directory. Reuse primitive constraints through the existing contribution schema URN; alias the already-authoritative artifact and guidance definitions rather than clone them.

All records are closed (`additionalProperties: false`), all listed fields required except explicitly nullable fields. New request/proposal/approval/authorization/attempt IDs use UUIDv4. Existing actor/device/profile/workflow/execution identifiers stay opaque `Identifier`. Organization IDs remain lowercase UUIDs. Revisions are decimal-string `U64`, with semantic maximum 18446744073709551615. Times are UTC RFC 3339 `Z`. Identity/proposal text is plain text, maximum 4,096 Unicode code points; safe reasons maximum 512. JSON duplicate keys, unknown fields, unsafe numbers, unsupported schemas, and invalid encodings reject before policy evaluation. Bound metadata requests to 256 KiB and individual action arguments to 16 KiB; do not alter preexisting larger contribution transport limits.

Preserve `ExecutionContextV1` exactly:
```text
{kind:"job", job_id, case_id, agent_version}
| {kind:"assist", assist_session_id, assist_plan_id, assist_plan_version, playbook_version}
```
Preserve the browser/HUD digest:
```text
action_sha256 = "sha256_" + lowercase_hex(SHA256(JCS({
  action_id, execution_context, application_profile_id,
  application_profile_version, document, surface_generation,
  target_key, record_key, expected_state, environment, operation, argument
})))
```
Copy nested document/expected-state/operation/argument variants from `browser-extension.md:1017-1060,1269-1298` and HUD assist definitions. Do not add actuation primitives or generic arbitrary JSON arguments. The digest deliberately excludes reservation ID, ephemeral target handle, authorization/approval references, and deadline. API-adapter action digests use the same `sha256_` prefix over JCS of the explicit tagged projection `{kind:"adapter", action_id, execution_context, application_id, adapter_capability_version, record_key, expected_state, environment, operation_id, argument_sha256}`. `argument_sha256` is bare lowercase SHA-256 of the adapter's canonical typed argument. Identity obtains trusted `ActionPolicyFactsV1` from the enforcing adapter, not the model; it cannot determine amount/destination/risk from an opaque hash alone. The facts bind that argument hash and action digest to the adapter's validated target/argument/preconditions, declared risk floor, action category, record type, destination, amount/currency, and eligibility revision. Missing facts deny; no invented generic adapter argument semantics.

Formal approval states are `pending → approved|rejected|changes_requested|expired|invalidated`; only approved may become `consumed`, and an approved unconsumed decision may become expired/invalidated. Pending expires after 24 hours; approval expires after 15 minutes without consumption. Organizations may shorten both. `request_changes` closes that proposal; a revised proposal gets a new revision/digest and fresh review. Rejected/expired proposals cannot be revived. Revalidate exact record revision, material values, document/surface generations, execution context, policy, actor authority, and key validity. Changed bindings invalidate rather than silently transfer an approval. Conservatively invalidate on record-revision changes even when the adapter cannot prove whether the change is harmless.

A newly refreshed document/record binding changes the digest and requires a revised proposal, not recycled approval. Pending proposals may outlive their initial 30-second preflight facts; expired facts cannot authorize subsequent dispatch.

Bulk approval is default-off. Security Admin plus Workflow Owner explicitly allow homogeneous `(workflow, application, operation, risk, currency)` classes and relevant limits; no inferred amount thresholds. At most 100 visible selected items per review operation. No unresolved exceptions or heterogeneous authority hidden in a batch. Validate all proposed decisions and commit all approval records atomically or reject the review request; subsequent dispatch/consumption remains independent per item and never implies all-or-nothing external business effects. Use separate domain-governance approval subjects below rather than fabricating job/assist contexts for releases, rules, or permission policy.

Repeated remits from one person count as separate authorized remits only where policy permits it.

### 3a. Complete the bounded support-type registry

Add these closed definitions to the identity schema. `Id` below means existing `Identifier`, `Rev` means U64, `UUID` means UUIDv4, `Utc` means existing UTC format, `Hash` means bare SHA-256, `Text` means plain text ≤4,096 code points, and `Secret` means unpadded base64url encoding of 32 random bytes. Nullability is explicit; arrays are unique, at most 128 unless another limit is stated.

### 4. Make current authority and one-use dispatch durable

Document PostgreSQL tables with exact columns/types/checks/FKs/indexes and example transactions, using these names:
- Private global `identity_person`, `identity_login_subject` (unique issuer/subject; email not unique authority).
- Tenant-owned `identity_organization`, `identity_membership`, `identity_team`, `identity_team_member`, `identity_invitation`, `identity_role_assignment`, `identity_restriction`, `identity_approval_delegation`, `identity_policy_version`, `identity_authority_guard`, `identity_device`, `identity_review_key`, `identity_execution_principal`, `identity_action_fence`, `identity_approval_proposal`, `identity_approval`, `identity_action_authorization`, `identity_action_consumption`, `identity_legal_hold`, `identity_signing_key` (public metadata/Vault reference only), `identity_emergency_account`.
- Reuse Control Plane session/idempotency storage and existing `domain_outbox`/`domain_inbox`; do not invent another generic event broker or duplicate sync serialization ledger.

Every tenant PK/FK begins with `organization_id`. UUID columns for organization/new UUID IDs; opaque identifiers TEXT with existing pattern bounds; U64 `NUMERIC(20,0)` plus full range check; UTC `TIMESTAMPTZ`; digests validated TEXT; booleans BOOLEAN; closed validated typed documents JSONB only where variable typed policy/proposal structure earns it. Approvals reference exact proposal revision/digest; authorizations reference exact action digest and approval; consumption has unique `(organization_id, authorization_id)` and unique `(organization_id, attempt_id)`. Crucially, `identity_action_fence` has primary key `(organization_id, execution_context_sha256, action_id)`, stores immutable `action_sha256`, state `prepared|admitted|reconciled`, winning authorization/attempt IDs, and revision. `execution_context_sha256` is bare SHA-256(JCS(execution_context)). All tokens for the same logical action share this fence; different token nonces cannot duplicate its dispatch. Digest changes conflict. Unique idempotency `(organization_id, actor_id, operation, command_id)` binds a request digest; altered payload gives 409. Lineage FKs use RESTRICT; references to expired display content use nullable foreign keys plus retained digest/ID, not cascade deletion of approvals/consumption.

PostgreSQL RLS applies to every tenant table, including joins and background work. Set organization context transaction-locally only from validated authenticated context. Missing context denies. Runtime roles are neither owners nor `BYPASSRLS`; migration/maintenance credentials stay separate. Private global subject lookup uses a narrowly privileged authentication adapter, not tenant-query bypass. Every cache/search/read-model fetch also enforces current scope. A report source graph edge grants no access to its target.

Use `READ COMMITTED` and transactionally locked authority-guard rows. All permission-affecting changes update the appropriate organization/member/device/policy/eligibility guards in the same transaction as canonical state. Lock guards in sorted `(organization_id, guard_kind, guard_id)` order; authorization/consumption takes `FOR SHARE`, restrictions take `FOR UPDATE`. Read canonical facts only after guard acquisition; insert audit/outbox records before commit. Owner modules update their eligibility guard with their canonical lifecycle transition, not through asynchronous permission caches.

Authorization issuance locks/checks current facts, signs under a bounded signer timeout, inserts the exact authorization row plus audit, then commits. A signed token whose transaction did not commit cannot be consumed. Consume locks/revalidates all current authority and the authorization/proposal rows, checks exact context/digest and deadlines, consumes approval and nonce, appends the durable attempt/audit, and commits before its one external dispatch. A later revocation wins against every not-yet-consumed action even if an unexpired signed token exists.

Lock and consume the logical action fence as well as the individual nonce/approval. Orchestrator/HUD issues stable action IDs for pinned step intents; a runner/model cannot mint replacement IDs to bypass a consumed fence. On a definitely-not-submitted or independently verified no-effect outcome, the owning coordinator may create a new action intent with a new action ID, `retry_of_action_id`, and reconciliation-evidence reference; Identity verifies that record before new authorization. No automatic unconsume, digest rebinding, or new attempt while an earlier external outcome is unknown.

This consume transaction is the explicit authorization linearization point. Once an action is consumed/admitted, external dispatch may already be in progress; revocation requests best-effort abort but cannot promise rollback or recall. No follow-on action obtains authority. The enforcement adapter checks local pause/reservation/context again immediately before actuation. Offline, connection loss before consume response, stale generations, or missing policy authority blocks dispatch. No network call to the external business system occurs while holding database transactions.

Persist dispatch intent before sending. A consumed authorization is never automatically reissued/replayed after crash, lost response, or ambiguous external result. Reconcile status and use Outcome Verification/readback; report `Outcome Unknown` when external effect cannot be established. Permission consumption, HTTP success, primitive click completion, and verified business outcome remain distinct states. No unsupported exactly-once or distributed transaction promise.

Cloud enforcement adapters use infrastructure-authenticated mTLS/workload identity; the local native execution gateway uses registered device-key request proof plus an execution-audience Oryn token, with the existing OS/helper/code-signature trust assumption rather than a false remote hardware-attestation claim. `identity_execution_principal` has `principal_kind:execution|service`, principal ID, organization, workload/device binding, owner actor/schedule or service-policy authority, nullable execution context, immutable action-intent allowlist, fixed inference-purpose/operation allowlist, status, issue/expiry, and revision. Execution principals require a context; inference-only service principals require null context and cannot execute business actions. Neither can hold human administrator roles. Removing responsible authority pauses affected work; simulation credentials cannot target production endpoints.

### 4a. Keep restore from resurrecting revoked or consumed authority

Use Infrastructure's existing immutable audit-storage responsibility as an independent authority-recovery journal, outside the PostgreSQL backup/restore failure domain. This is a required owner contract, not an implemented storage claim. Journal only typed identity/control transitions and logical action-fence records, encrypted under organizational audit storage policy; never private captures, tokens, inference scopes, or review-key material.

Define `AuthorityJournalEntryV1` (`identity.authority-journal-entry.v1`): `{organization_id, recovery_epoch:UUID, sequence:Rev, previous_entry_sha256:Hash|null, mutation_id:UUID, kind:authority_changed|action_admitted|governance_consumed|organization_deleted, record_after_images:<closed union of affected identity row types or action-fence rows>, committed_at:Utc}`. The record-after-image variants use exact schema/SQL field mappings, not arbitrary JSON. A signed receipt `SignedAuthorityCheckpointV1` (`identity.authority-checkpoint.v1`, receipt-key purpose) contains `{organization_id, recovery_epoch, through_sequence:Rev, entry_sha256:Hash, persisted_at:Utc, request_nonce:Secret}`. Infrastructure exposes idempotent append by `(organization_id, recovery_epoch, sequence)` with digest conflict rejection, and a fresh-nonce-bound latest-checkpoint/read-contiguous-range interface.

For authority mutations, governance consumption and logical-action admission: commit the state/fence plus a `durability_pending` guard and journal outbox row in PostgreSQL; append its exact committed after-image to independent journal; only after durable signed receipt mark the guard durable and acknowledge success or release the first dispatch response. No new privileged action passes a pending durability guard. Restrictions already deny locally while receipt is pending. No external business call occurs while awaiting journal. Receipt/ack loss is idempotent and conservative; consumed attempts remain consumed, never resent automatically. A failed journal dependency returns restricted/503/unknown delivery, not a durable-success claim. Ordinary non-authorizing read/denial audit export can remain asynchronous.

On restore, keep all privileged traffic and new leases disabled. Obtain the independent latest checkpoint, replay a complete verified journal range into the restored database through that checkpoint, and rebuild membership/policy/revocation/action fences. Invalidate all pre-restore sessions, pending approvals, unconsumed tokens and workload assignments; publish a fresh authenticated recovery/control epoch without lowering revision floors. Restore does not reset keyset/access/policy generations. Reconcile every admitted action with its owning coordinator and external readback before any retry. Missing/gapped/unverifiable journal or an unreconciled lost authority interval yields `IDENTITY_RECOVERY_INCOMPLETE`; keep affected organizations/capabilities blocked. Never treat a new UUID epoch or the restored backup itself as evidence that no revocation/dispatch was lost.

### 5. Issue signed privacy, guidance, inference, and trust artifacts

Use existing `{schema_id,key_id,payload,signature}` envelopes. Exact signing preimage is UTF-8(schema_id) + one LF byte + RFC 8785 JCS(payload). Ed25519 signs these bytes, not a prehash and not Vault's textual wrapper. `signature` is unpadded base64url of 64 raw bytes; `public_key` encodes 32 raw bytes. The existing key registry binds organization/key purpose; unsigned key ID is never a trust lookup URL. Add this rule to current normative sync/HUD/privacy docs; it already exists in the contribution specification plan and privacy text.

Vault Transit reference: Ed25519, `derived=false`, `exportable=false`, `allow_plaintext_backup=false`, separate root/policy/publisher/receipt mounts or key ACLs, workload-authenticated narrowly scoped sign endpoints. Strip `vault:vN:` and decode/re-encode raw signature into the wire format; pin requested key version to `key_id`. Application/DB stores public key, purpose, status, validity and Vault reference only. Signer outage blocks new authority; never use unsigned or application-memory fallback keys. This is software-managed Ed25519 inside Vault, not a hardware-isolation/FIPS certification claim.

Deployment-packaged roots establish initial trust; no TOFU. An infrastructure-controlled isolated root signing identity issues `sync.trust-keyset.v1` with maximum 24-hour validity. Identity application cannot call the root signer. Preserve purposes `device|root|policy|publisher|receipt` and statuses `active|verify_only|revoked`. Policy keys sign identity/approval/capture/retention/artifact/guidance/inference authority; publisher keys sign bundles; receipt keys sign delivery receipts; device keys sign review and local authorization-context attestations. Enforce schema/purpose, organization, key validity, and applicable revision floors before accepting a signature.

Policy/publisher/receipt keys rotate every 30 days with at least 24-hour overlap. `verify_only` cannot issue new artifacts but may verify still-valid historical ones. Received compromise revocation prevents new use immediately; a historical signature alone does not restore current access. Normal root rollover requires a newer trusted keyset signed by the currently pinned root, prepublished next root and signed application trust-bundle update. Compromised root recovery requires a signed application/trust-bundle update through the independently pinned code-update trust; never let a compromised root authorize its own recovery. Persist revision/keyset/access/control high-water marks using existing OS-vault-anchored catalogs. Restore of older ciphertext must not lower them; keyset rollback or untrusted clock fails closed. Central restore follows the independent journal checkpoint protocol in slice 4a before traffic resumes.

- `SignedCapturePolicyLease`, `privacy.capture-policy.v1`: organization/actor/device/enrollment, U64 policy/notice revisions, issue/expiry, six existing permitted categories, mandatory exclusion catalog revision, excluded app IDs/URL patterns, raw-retention bounds, extension permission, revocation generation. Default maximum 24 hours, administrator-shortenable, clamped to key validity. It grants organizational eligibility, not employee consent.
